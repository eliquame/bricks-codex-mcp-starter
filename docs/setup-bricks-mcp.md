# Bricks MCP Setup

This is the manual/reference setup guide. The normal automated path is the root `START-HERE.md` workflow.

This guide intentionally avoids site-specific credentials.

## On the WordPress / Bricks site

1. Open **Bricks > AI > Configuration**.
2. Enable **Bricks abilities**.
3. Install and activate the **WordPress MCP Adapter** when prompted.
4. Confirm the MCP server reports **Connected**.
5. Create/select a dedicated WordPress user for the AI client where practical.
6. Assign only the WordPress + Bricks permissions required for the current workflow.
7. Generate a WordPress Application Password for that user.
8. Select **Codex** as the client.
9. Use **Paste config**.

Bricks recommends `Paste config` for config-file clients because it keeps credentials out of the chat prompt.

## Codex config

Typical global Codex configuration paths:

Windows:

```text
%USERPROFILE%\.codex\config.toml
```

macOS / Linux:

```text
~/.codex/config.toml
```

Merge the site's generated MCP block with the existing config. Do not overwrite unrelated settings.

Example shape only:

```toml
[mcp_servers.example-site]
command = "npx"
args = ["-y", "@automattic/mcp-wordpress-remote@latest"]

[mcp_servers.example-site.env]
WP_API_URL = "https://example.com/wp-json/mcp/mcp-adapter-default-server"
WP_API_USERNAME = "dedicated-ai-user"
WP_API_PASSWORD = "LOCAL-APPLICATION-PASSWORD"
```

Always use the exact values generated by the target Bricks site.

Do not:
- paste the real Application Password into chat;
- put the password in the endpoint URL;
- put it in command arguments;
- put it in global shell config;
- define the same MCP server name twice.

If Bricks generates `NODE_TLS_REJECT_UNAUTHORIZED=0` for a local/self-signed HTTPS site, keep it scoped only to that MCP server.

Never commit a real credential-bearing config block to Git.

## Reload and verify

After saving the config:

1. start a new Codex chat so the MCP server reloads;
2. if the server still does not appear, fully restart Codex.

Then perform read-only diagnostics using the available equivalents of:

- `bricks-start-here`
- `bricks/get-mcp-version`
- `bricks/list-ability-status`

If an ability is not exposed as a direct tool, use the MCP Adapter dispatcher when available.

Fix the MCP connection before installing Bricks skills or attempting site writes.

## Multiple sites

Codex can have multiple MCP server blocks in the same global `config.toml`.

Use:
- a unique MCP server name per site;
- a separate Codex project per site;
- project-root `AGENTS.md` rules that restrict each project to its assigned MCP server.
