# Copy to Codex — Bricks MCP Connection & Project Setup Wizard

Copy the text block below into a **new Codex chat**. It is designed to guide the user through the connection without asking them to paste WordPress credentials into chat.

```text
Act as an interactive setup wizard for connecting one WordPress / Bricks Builder site to Codex through the Bricks MCP integration and preparing a site-specific Codex project.

IMPORTANT SECURITY RULES

- Do NOT ask me to paste a WordPress Application Password, normal WordPress password, API key, token, or other credential into this chat.
- Do NOT print, echo, summarize, or expose any credential that may already exist in a local config file.
- Prefer the Bricks "Paste config" method instead of Bricks "Copy a prompt", because the latter may contain the WordPress username and Application Password.
- If you inspect a local config file, redact secret values from anything you show me.
- Do not modify the WordPress / Bricks site during setup except for actions I explicitly perform in the WordPress admin UI.
- Do not enable PHP abilities.
- Treat Bricks AI abilities as experimental; recommend local/staging for first setup and testing.

WORK INTERACTIVELY

Do not dump all instructions at once.
Complete each phase, verify it, then continue.
Only stop for user action when the action requires the WordPress admin UI, a secret, a restart, or a permission you do not have.

PHASE 1 — CHECK THE LOCAL CODEX ENVIRONMENT

1. Detect my operating system.
2. Confirm that I am using Codex and that a site-specific project/workspace is open.
3. If no suitable site project folder is open, ask me to create/open one before continuing.
4. Locate the Codex global configuration file:
   - Windows: %USERPROFILE%\.codex\config.toml
   - macOS/Linux: ~/.codex/config.toml
5. Determine whether the file already exists.
6. Do not overwrite or reset existing Codex configuration.
7. If you can safely open the file locally, do so. Otherwise give me the exact OS-specific command/path to open it manually.

PHASE 2 — PREPARE THE WORDPRESS / BRICKS SIDE

Guide me through these WordPress admin steps one at a time:

1. Open Bricks > AI > Configuration.
2. Enable Bricks abilities.
3. Install/activate the WordPress MCP Adapter if Bricks reports it missing/inactive.
4. Confirm the MCP server shows as connected.
5. Use a dedicated WordPress user for Codex where practical.

Explain that:
- the MCP client acts as the WordPress user behind the Application Password;
- WordPress capabilities + Bricks Builder Access + Bricks permissions all still apply;
- a full bootstrap audit may require more read access than routine editing;
- elevated/admin access should not be kept for normal routine work merely for convenience.

Do not change WordPress roles or permissions yourself unless I explicitly ask and the available tools support it.

PHASE 3 — CREATE THE CREDENTIAL WITHOUT SHARING IT IN CHAT

Tell me to:

1. In Bricks > AI > Configuration > Create a credential, choose the dedicated WordPress user.
2. Give the credential a recognizable name such as "Codex bootstrap".
3. Generate the WordPress Application Password.
4. Copy/save it immediately because WordPress only shows it once.
5. Select Codex as the client.
6. Use the Bricks "Paste config" option.

IMPORTANT:
Do NOT ask me to paste the generated config block into this chat.

PHASE 4 — MERGE THE BRICKS MCP CONFIG INTO CODEX

Guide me to copy the Bricks-generated Codex config block from WordPress.

Then help me place it in the Codex global config file.

Rules:

- Preserve every existing setting already in config.toml.
- Add the Bricks MCP block as a separate new [mcp_servers.<unique-site-name>] section.
- Never place it inside another MCP server section.
- Ensure the MCP server name is unique for this site.
- The generated block normally contains:
  - WP_API_URL
  - WP_API_USERNAME
  - WP_API_PASSWORD
  - command = "npx"
  - args using @automattic/mcp-wordpress-remote
- Use the exact endpoint and config values generated by the target Bricks site.
- Do not invent a URL or username.
- Do not move WP_API_PASSWORD into command arguments, an endpoint URL, or global shell config.
- If Bricks generated NODE_TLS_REJECT_UNAUTHORIZED=0 for a local/self-signed development site, keep it scoped only to that MCP server.

If you can open the local config file:
- show me where the new block belongs;
- let me paste the credential-bearing block locally;
- do not echo the secret back to chat.

If you cannot safely edit/open it:
- tell me to append the generated block at the end of config.toml;
- have me save the file;
- then continue.

PHASE 5 — RELOAD AND VERIFY MCP

After config.toml is saved:

1. Tell me to start a new Codex chat so the MCP server is reloaded.
2. If the server still does not appear, tell me to fully restart Codex and try again.
3. In the fresh session, perform READ-ONLY discovery.
4. Verify the Bricks MCP connection using the available diagnostic abilities/tools, including the equivalents of:
   - bricks-start-here
   - bricks/get-mcp-version
   - bricks/list-ability-status
5. List the directly exposed Bricks tools/abilities if available.
6. Do NOT modify the site during this verification.

If connection fails:
- check whether the target MCP server is loaded;
- check config syntax;
- check endpoint/user mismatch;
- remind me I can regenerate the Application Password;
- do not ask me to reveal the password.

PHASE 6 — INSTALL / VERIFY BRICKS SKILLS

First check whether client-side skills whose names start with "bricks-" are already loaded.

If loaded:
- list them;
- continue.

If not loaded:
1. Prefer the official Bricks workflow:
   - open Bricks > AI > Skills;
   - copy the install prompt;
   - follow that prompt.
2. If this Codex client can install skills directly and internet/GitHub access is available, follow the current Bricks skills repository README:
   https://github.com/codeerhq/bricks-skills
3. Use the latest appropriate public release/install method for this client.
4. Report the installed skill names.
5. Start a fresh Codex chat after installation if required.
6. Verify loaded skills in the new chat.

Skills are workflow guidance; they do not grant new WordPress/Bricks permissions.

PHASE 7 — INITIALIZE THE SITE PROJECT

The project must have a project-root AGENTS.md before normal work.

Preferred source:
- project-starter/AGENTS.md from the bricks-codex-mcp-starter repository.

If this starter repository is available locally or through authorized GitHub access:
1. Copy project-starter/AGENTS.md to the root of the current site project as AGENTS.md.
2. Copy project-starter/docs/bricks/README.md into docs/bricks/README.md.
3. Do NOT copy credentials or site-specific audit output from another project.

If the starter repository is not accessible:
- tell me exactly which two starter files I must copy manually from the repository;
- wait until I confirm they are present.

Do not replace an existing site-specific AGENTS.md without first reading it and preserving useful project-specific instructions.

PHASE 8 — FINAL SETUP CHECK

Verify and report only non-sensitive status:

- target project folder
- MCP server name
- Bricks MCP: CONNECTED / NOT CONNECTED
- diagnostic calls: OK / FAILED
- Bricks skills: LOADED / NOT LOADED
- project-root AGENTS.md: PRESENT / MISSING
- docs/bricks starter directory: PRESENT / MISSING
- WooCommerce status only if already discovered without extra write access
- any permission limitation discovered

Never report the Application Password.

When everything is ready, tell me the next recommended action is to run the generic full-site bootstrap audit from:

prompts/00-full-site-bootstrap-audit.md

Do not start that audit automatically unless I ask.
```

## Why this wizard avoids Bricks “Copy a prompt”

Bricks can generate a convenience prompt containing the connection details. That may include the WordPress username and Application Password. This starter instead recommends the config-file route so the secret can stay in the local Codex MCP configuration rather than being pasted into chat.
